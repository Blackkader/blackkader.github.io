Looking at this main function, it looks messy with all those weird sub_1C40 calls, but if you look closer, the pattern is pretty obvious : First, it calculates some sizes : - sub_1DB0 gets the total file size of argv[0]. - sub_1CF0 parses the ELF header to get the size of this stub itself. - So v5 - v7 is literally just the size of the payload appended to the binary . Now what is sub_1C40 with those huge numbers like 3735929052LL (0xDEADC0DC) ? It’s an obfuscated direct syscall dispatcher ! It xors the syscall numbers at runtime with a constant (0xDEADC0DE) to call open, mmap, memfd_create, write, munmap, and execveat without leaving standard libc imports . Then we have this juicy part :

v19 = getenv(name: "TRUSTISKEY");
if ( !v19 )
  v19 = getpass(prompt: "type 'letmethink' : ");
v60 = v5 - v7;
v21 = sub_1E40(unk: v58, unk: v5 - v7, unk: v19);

It takes our input string (or checks if TRUSTISKEY env var is set) and passes it to sub_1E40 along with the appended data . That's the decryption routine (RC4) . Right after decrypting , it loops and overwrites v19 with random chars from characters[] to wipe the password from memory . And finally :

v27 = v26(unk: v24, unk: "asdf", unk: v25, unk: 0); // memfd_create("asdf")
...
v34 = v33(unk: v31, unk: v30, unk: v58, unk: v60); // write(fd, decrypted_elf, size)
...
v52(unk: v48, unk: v62, unk: v50, unk: v51, unk: a3); // execveat(fd, "", ...)

It creates an anonymous in-memory file with memfd_create, writes the decrypted ELF directly into that file descriptor , wipes the decrypted buffer with random bytes, and runs it using execveat ! So this whole binary is just an in-memory unpacker / loader . Now do we need to reverse the decryption function and write an unpacker script ? We can, but dynamic analysis is our ally here ! If the binary is decrypting the full ELF in memory and writing it into a file descriptor, we can just intercept that write syscall and grab the binary right before it executes .

Let's trace the relevant syscalls to see what's happening :

Look at that write syscall : it is writing 25177232 bytes (around 25 MB) starting with \x7fELF directly into file descriptor 4 ! The entire unpacked binary is handed to us on a silver platter in a single syscall . Next move ? DUMP IT OUT using gdb :

Then we hit the breakpoint few times until we reach the desired write call. In the x86_64 calling convention for syscalls : - $rdi = fd - $rsi = buffer pointer (where the decrypted ELF starts) - $rdx = count (size of the buffer in bytes)

So at the right breakpoint we just dump the memory from \$rsi to \$rsi + \$rdx into a file :

dump memory unpacked.elf $rsi $rsi+$rdx

IMPORTANT : At this point,IDA stops decompiling and gives up.
Go uses RBX to return errors, but IDA thinks RBX never changes across function calls. Since RBX had a non-zero value right before calling os.Open, IDA assumed the error check would always fail and crash into a panic. Because of that, IDA treated the rest of the function as unreachable code and deleted it from the view. Once we NOP out the error jump at 0xF708B4, IDA stops panicking and decompiles the remaining parts cleanly.

So The binary takes embedded data (random.dat), decrypts it via a 2-byte repeating XOR key (0xD3, 0xAD), and drops it to disk as generator.py. It then executes it via python3 generator.py. The execution of generator.py produces a compiled hello.pyc. The binary immediately opens hello.pyc, reads the first 4 bytes—which represent the Python bytecode magic number and deletes both generator.py and hello.pyc. These python magic numbers are prepended to a 12-byte hardcoded suffix to form the 16-byte AES-128-CBC IV.
